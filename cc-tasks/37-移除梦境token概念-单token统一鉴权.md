# Brief 37 · 移除「梦境 token」概念:单 token 统一鉴权

> 背景:release 复测(20260719)。已核实:后端梦境端点要求 scope `activity`,
> desktop token 的 profile 本就覆盖——「梦境 token」与「现实 token」从来是
> 同一个值,客户端维护两份是伪需求;且 release 包里 Brief 35 §3 加的梦境
> token 入口实测缺失(是否构建遗漏已不重要,方案改为整体移除)。
> **后端零改动,不去掉鉴权**——去鉴权动的是安全面,收益为零;该删的是
> 客户端里多余的第二个 token 概念。独立小单,无依赖。

## 1. 🟡 拆除梦境 token 双入口

- 移除 Brief 35 §3 引入的:系统设置里的「梦境 token」输入框、梦境进入页的
  就地填写弹窗、以及配置存储中的独立梦境 token 字段。
- 全部梦境相关请求改用主 token(与聊天/其他请求同一份配置、同一请求封装,
  走 Brief 35 §2 的共享请求层)。
- 配置迁移:旧版本已存过梦境 token 字段的用户,启动时静默丢弃该字段
  (值本来就相同,无信息损失),不弹任何提示。
- 梦境请求 401 的处理并入 Brief 35 §2 的统一策略(停止重试 → 弹主 token
  引导页),不再有梦境专属的 token 引导分支。
- 删除对应 i18n key(确认无他处引用后清理)。

## 验收

- 全新安装只填一个 token:聊天、入梦、梦境对话、退梦全链路可用。
- 旧配置(含梦境 token 字段)升级后正常启动、梦境可用、字段被清理。
- 界面上再无「梦境 token」字样;`npm run check:naming` / 现有校验通过。
- release 构建产物(非 dev 模式)实测包含上述行为——上次入口缺失的教训:
  **验收必须打一次 release 包验证**,不许只在 dev 跑。
