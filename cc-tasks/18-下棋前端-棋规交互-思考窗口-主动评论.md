## 排查结论（现状）

1. **王车易位"点王再点车没反应"**：后端 python-chess 完全支持，`legal_moves` 里王车易位是王的 UCI（`e1g1`/`e1c1`），不是"王到车"。`ChessPage.tsx::handleSquareClick` 只把 `m.slice(2,4)` 当目标格——点车（己方棋子）走的是"重新选中"分支。**用户点 g1 其实是能易位的，但没人知道**。
2. **吃过路兵**：同类问题——UCI 目标格是斜后方的**空格**（如 `e5d6`），用户直觉是点**对方的兵**（d5）。点空格其实能走。
3. **升变全坏**（排查中新发现）：合法走法是 `e7e8q` 等 5 位 UCI，目标高亮取 `slice(2,4)` 后点击发出 `e7e8`（4 位、无升变子力）→ 后端 422 `无法解析走法`。兵推到底线永远失败。
4. **思考窗口为零**：后端 pending 机制（`pending_ai_turn` + `/ai_move`）就是给"落子前思考"留的窗口，窗口内的活动聊天可通过 style tilt 影响 AI 这一手（gomoku 已有、chess 由 Brief 43 §E 补上）。但 ChessPage 在 move 返回后**立即** `triggerAiMove`；GomokuPage 干脆用 auto 模式（AI 在 `/move` 响应内落子），窗口都是 0，"打断"无从发生。
5. **角色不主动说话**：前端从不触发评论；Brief 43 §D 提供 `POST /activity/{chess,gomoku}/comment`，是否开口由后端策略裁决（关键时刻必评 + 20% 低频 + ≥2 步冷却），前端只管每次 AI 落子/终局后调一次并展示。

用户已拍板：思考窗口 **3–8 秒随机**。

## §G ChessPage 棋规点击交互（可立即做）

文件：`src/windows/activity/components/ChessPage.tsx`

改造 `handleSquareClick` 的选中/目标模型——选中棋子时保存**完整 UCI 列表**而不是只存目标格：

```ts
const [selectedMoves, setSelectedMoves] = useState<string[]>([]); // 该子全部合法 UCI
// legalTargets 由 selectedMoves 派生：new Set(m => m.slice(2,4))
```

点击目标格 `sq` 时的匹配顺序：

1. **普通/升变**：`candidates = selectedMoves.filter(m => m.slice(2,4) === sq)`。
   - 有 5 位候选（升变）→ 发送 `fromSq + sq + 'q'`（默认后升变；后续如要弹选择框另开任务，本期默认后即可，操作说明里写明）。
   - 否则发送 `fromSq + sq`。
2. **王车易位（点车也生效）**：选中子是王（`K`/`k`）且点击格是**己方车**时，映射：点 h1→试 `e1g1`，a1→`e1c1`，h8→`e8g8`，a8→`e8c8`（用 fromSq 拼，不要写死 e1：非标准局面王可能不在 e1 时直接跳过该映射）。映射结果在 `selectedMoves` 里才发送。
3. **吃过路兵（点对方兵也生效）**：选中子是兵，点击格是**对方兵**且存在候选 `m`，满足 `m[2] === 点击格的列` 且 `m.slice(2,4)` 是空格斜进（即 `selectedMoves` 里有目标列相同、目标行 = 兵前进一行的走法，且该目标格无子）→ 发送该 `m`。
4. 都不匹配 → 维持现有"重选/取消"逻辑。

**高亮同步**：`legalTargets` 派生时额外加入上述两类"别名格"（己方车格、可过路吃的对方兵格），让用户看得见能点。目标环/圆点样式沿用现有 isTarget 渲染即可。

**验收**：
- 标准开局快速走到可易位局面，点王→点车、点王→点 g1 两种都成功；
- 构造过路兵局面（e2e4 … e4e5 d7d5 后 e5 兵），点 e5 兵→点 d5 敌兵、点 d6 空格都成功；
- 兵到底线自动升后，不再 422；
- 走棋记录里 SAN 正确显示 `O-O` / `exd6 e.p.` / `e8=Q`。

## §H AI 思考窗口 3–8s（可立即做）

### ChessPage

- 现状 `move` 返回 `pending_ai_turn=true` 后立即 `triggerAiMove(sid)`。改为：
  ```ts
  const delay = 3000 + Math.random() * 5000;  // 3–8s
  aiTimerRef.current = setTimeout(() => triggerAiMove(sid), delay);
  ```
- 新增独立状态 `aiThinking: boolean`（不要复用 `loading`：**窗口期间陪聊输入必须可用**——这是"可打断"的意义，聊天里说"认真点"会通过 style tilt 影响这一手）。棋盘 disabled 条件加 `aiThinking`；回合提示显示"对方思考中…"（角色名用 `getActiveCharacterName()`）。
- 清理：session 关闭 / 组件卸载 / 再来一局时 `clearTimeout`。
- `triggerAiMove` 失败时清 `aiThinking` 并显示错误（现有 error 通道）。

### GomokuPage

文件：`src/windows/activity/components/GomokuPage.tsx`

- `handleStart` 的 `gomokuApi.start({...})` 加 `ai_response_mode: 'pending'`（现在默认 auto，AI 在 /move 内瞬间落子）。
- `handlePlace` 后若响应 `pending_ai_turn === true`：同 ChessPage 的 3–8s 延迟后调 `gomokuApi.aiMove(session_id)`（API 若缺见 §J），期间落子禁用、陪聊可用。
- gomoku 的 style tilt 后端已有：窗口内 /chat 产生的 `ai_style_tilt` 会被 `/ai_move` 读取——不需要前端做任何事，聊天照发即可。

**验收**：落子后 AI 3–8s 才应手；窗口内在陪聊面板发消息不被禁用；发"温柔点/认真点"后（模型给出 tilt 时）下一手风格字段变化（debug 面板或响应里 `last_move.style` 可见）。

## §I 主动评论接入（依赖 Brief 43 §D）

1. 每次 **AI 落子完成后**（chess `triggerAiMove` 成功、gomoku `aiMove` 成功）以及 **终局时**（status completed，无论谁走的最后一手），异步调 `POST /activity/{game}/comment`。失败静默（console.debug），不打扰对局。
2. `comment === null` → 什么都不做（后端策略决定这步不说话）。
3. `comment` 非空 → 显示到右侧陪聊面板。跨组件传递用 CustomEvent：
   ```ts
   // 页面侧
   window.dispatchEvent(new CustomEvent('activity-companion-push', {
     detail: { activityId, sessionId, text: comment, grounding } }));
   // ActivityCompanionPanel 侧：useEffect 监听，detail.sessionId === 当前 sessionId 时
   // append 一条 assistant 消息（复用现有 ChatMessage 渲染与 GroundingHint）
   ```
4. 节流在后端（关键时刻必评 + 20% + ≥2 步冷却），前端不要再加概率逻辑，避免双重削减。
